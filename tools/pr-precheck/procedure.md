# Procedure: how this skill grades a PR package

## Read order

1. In live mode, read `scope.md` first before anything else. If the `Repo:` line is an unfilled placeholder or the work belongs to a different repo, stop and say so. Then read `voice-guide.md`. In eval mode, skip both. The bundle is the whole world, you read nothing outside it.
2. Collect the package. In live mode: `plan.md` (with `## Deviations`), the output of `git diff main...HEAD` and `git diff main...HEAD --stat`, `pr_draft.md` (the title is the first line), `test_evidence.md`, the issue thread, the repo's PR template, and `docs/CONTRIBUTING.md`. In eval mode: the matching sections of the bundle (repo facts, issue, thread highlights, plan context, title, description, commits, diff, test evidence). If a part is missing, write "missing: \<part\>" and carry on. Don't invent it.
3. Read the issue and the thread highlights first. Write one line for what the issue asks to be fixed. This is the fixed baseline for what the PR is supposed to do.
4. Read the repo-facts block (live mode: the PR template and CONTRIBUTING). List each stated ask as one line: each template section, each issue-reference ask, each changelog, what's new, test, docs, or schema ask, each check command, and each AI-use rule, noting exactly what it demands. If the repo states none, write "no stated asks". You need this list for `Template complete`, `Repo asks met`, `Repo checks run`, and `AI disclosure`.
5. Read the plan next: its scope, its not-in-scope line (verbatim), its files list, each deliverable it names (changes, tests, docs, changelog), its test plan with the repro and controls it names, and its Deviations notes. Write the list of deliverables, one per line.
6. Read the diff before the description. Write one line per changed file, then one line per hunk saying what it does. Mark each hunk as: in the plan's scope, in a Deviations note, or neither. Reading the diff first stops the description's framing from shaping what you think the diff does.
7. Read the commits (the messages often name work the diff then holds), then the description (or the title and description in `pr_draft.md`). List every claim it makes: "exactly as planned", "no other changes", "tests added", "CHANGELOG entry added", "docs updated", each ticked box.
8. Read the test evidence last. For each repro the plan names, write down whether a before output and an after output are present, and what each one shows.

## Evidence gathering

1. For `Diff within plan`, put the diff's hunk list next to the plan's scope, its files list, its not-in-scope line, and its Deviations notes. Every hunk you marked "neither" is a drift candidate. For each deviation note, check whether the description restates it. Also check whether any commit message names work you cannot find in the plan.
2. For `Plan delivered`, put the plan's deliverables list next to the diff's file list. For each deliverable, write whether a hunk delivers it. For each one with no hunk, record whether a Deviations note or the description says it was left out and why.
3. For `Description matches diff`, put the description's claims list next to the diff's hunk list. For each claim, write the hunk that backs it, or "no hunk". For each hunk the description never mentions, record whether a recorded, restated note covers it. For any test the description cites, read the test and record whether it exercises the claimed change.
4. For `Repro before and after`, put the plan's named repros next to the test evidence. For each repro, copy the before output, the after output, and the expected-after the plan states. Note whether the after output differs from the before and shows the fix working, and whether the case run is the same case the plan names. For each control the plan names, record whether its outcome is stated.
5. For `Repo checks run`, put the check commands from your asks list, the suite, and the plan names next to the test evidence and the description's Testing section. For each, copy where its command appears and what outcome is stated or pasted. Record any ticked box with no output behind it, and any failure or skip that is not reported.
6. For `Clean diff`, scan every added and removed line and tag each as: debug output, commented-out code, dead or unused code, `TODO`/`WIP` note, formatting-only change (whitespace, reflow, import reorder) on code the fix does not otherwise change, hunk that serves no part of the plan, or part of the fix. Anything not tagged "part of the fix" is debris. A comment that explains the fix is part of the fix.
7. For `Template complete`, put the template's sections and issue-reference ask next to the description. For each section, write whether it has real content for this change, a placeholder, or nothing. Write whether the issue is referenced the way the repo asks.
8. For `Repo asks met`, put each changelog, what's new, test, docs, or schema ask from your list next to the diff's file list. For each, write the hunk that meets it or "no hunk". For checklist asks no diff can show, record whether the description states it and whether anything contradicts it.
9. For `AI disclosure`, find the repo's AI-use rule in your asks list, and write exactly what it demands (disclosure, tool, extent, own words). Then find the description's disclosure statement and copy it. In live mode, the course always asks for the disclosure, so look for it in Notes for Reviewers whatever the repo's policy says.
10. For `Title says what and where`, copy the title and write what it says changed and where, then check it against the diff's file list.

## Check execution

1. Run the checks in this order: `Diff within plan`, `Plan delivered`, `Description matches diff`, `Repro before and after`, `Repo checks run`, `Clean diff`, `Template complete`, `Repo asks met`, `AI disclosure`, `Title says what and where`. Grade each one from the evidence you gathered for it. You don't need to re-read the whole package for each check, except `Diff within plan` and `Clean diff`, which always read the whole diff.
2. Grade each check pass, fail, or `unclear`, applying only that check's pass condition from `rubric.md`. Do not grade on polish, length, formatting, or confidence. A short plain PR can be ready, and a long confident one can be hiding drift or untested claims.
3. If the package doesn't state the thing a check needs, grade fail. A claim is graded by what the diff or the output shows, not by what the description says. If a part the check reads against is missing from the package (no diff, no plan, no test evidence), grade `unclear` and say which part is missing.
4. If the PR does less than the issue or the plan asked, don't fail it for that alone. Pass `Plan delivered` if a Deviations note or the description says what was left out and why. A disclosed, necessary deviation passes `Diff within plan`. Debris and unrelated hunks still fail `Clean diff` even when disclosed.
5. Treat a check that passes by its stated condition as a pass, even if the PR feels wrong. Treat one that fails as a fail, even if the PR feels fine. If the rubric seems wrong, say so in the summary and don't change the grade.
6. For every grade, write one line that quotes the package's own words or output: a plan line, a diff line, a line of test output, or a sentence of the description. Do not use words of your own as evidence. If you cannot name a deciding fact, the check is `unclear` not pass.
7. If the procedure doesn't cover a step you need, say so in the summary and continue with the nearest written step. Do not make up a step.

## Verdict assembly

1. Apply the verdict rule from `rubric.md`: accept only if every required check is a pass. Any required fail or `unclear` makes the verdict reject. `Title says what and where` is preferred and never changes the verdict.
2. If the verdict is reject, name the deciding check. If more than one required check failed, the deciding check is the first failed one in the execution order above, and the rest are listed after it. Quote its evidence line: for `Diff within plan`, the hunk and the plan line it is missing from; for `Repro before and after`, the repro the plan names and what the evidence shows instead.
3. If the verdict is accept, quote the line that best supports the check that was closest to failing.
4. In live mode, add the voice findings from `voice-guide.md` to the summary, each rule the title or description breaks with the offending words quoted. They never change a grade or the verdict. In eval mode, there are no voice findings.
5. Print each check's grade with its quoted line, then any procedure gaps, then end with the fenced JSON block the frame requires: one entry per check named as in `rubric.md`, a one-line evidence value, and the verdict (accept for ready, reject for hold). Nothing follows the block.
